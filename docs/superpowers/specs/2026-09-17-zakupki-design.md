# Раздел «Закупки» — совместные оптовые закупки

Дата: 2026-09-17. Статус: согласовано, к реализации.

## Зачем

Оптовая цена начинается с объёма, который одной семье не нужен: машина щебня,
мешок крупы, рулон утеплителя, партия обуви. Сейчас такие закупки собираются в
чате — кто-то бросает клич, остальные отвечают вразнобой, инициатор сводит
список в блокноте и теряет его. Раздел даёт этому процессу форму: видно, что
собирают, сколько уже набрали, кто участвует, оплачено ли и на какой стадии
заказ.

## Модель

Одна закупка — **один товар**. Участник указывает только своё количество,
сумма считается сама. Прайс-листы с несколькими позициями сознательно не
делаем: они удваивают число экранов, а покрывают меньшую часть случаев. Если
нужно два товара — это две закупки.

### `purchases`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | INT UNSIGNED PK | |
| `organizer_id` | INT UNSIGNED → `families` | кто ведёт закупку |
| `title` | VARCHAR(200) | «Мёд гречишный» |
| `category` | VARCHAR(80) NULL | продукты, стройматериалы, одежда… |
| `unit` | VARCHAR(20) | единица: кг, шт, мешок, м³ |
| `price_per_unit` | DECIMAL(10,2) NULL | цена за единицу при опте |
| `target_qty` | DECIMAL(10,2) NULL | сколько нужно набрать |
| `deadline` | DATE NULL | до какого числа собираем |
| `supplier` | VARCHAR(200) NULL | поставщик или ссылка на прайс |
| `pickup` | VARCHAR(200) NULL | где забирать |
| `note` | MEDIUMTEXT NULL | условия, описание товара |
| `status` | VARCHAR(16) | `collecting\|ordered\|arrived\|done\|cancelled` |
| `created_at`, `updated_at` | DATETIME | |

Фото товара — в существующей полиморфной `images` с `owner_type='purchase'`,
хранение в Telegram (`TelegramMedia`), показ миниатюрами через `/tg-media/w…`.

### `purchase_orders`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | INT UNSIGNED PK | |
| `purchase_id` | INT UNSIGNED → `purchases` | |
| `family_id` | INT UNSIGNED → `families` | участник |
| `qty` | DECIMAL(10,2) | сколько берёт |
| `note` | VARCHAR(500) NULL | пожелание участника |
| `paid_at` | DATETIME NULL | организатор отметил оплату |
| `created_at`, `updated_at` | DATETIME | |

`UNIQUE (purchase_id, family_id)` — одна заявка на семью, её правят, а не
плодят. Собранный объём и суммы **считаются запросом по заявкам**; счётчиков в
`purchases` нет, поэтому рассинхрон невозможен (в отличие от `trips.seats_free`,
где счётчик приходится поддерживать руками).

## Жизненный цикл

```
collecting ──▶ ordered ──▶ arrived ──▶ done
     │             │           │
     └─────────────┴───────────┴──▶ cancelled
```

- **collecting** — идёт сбор. Житель записывается сам, меняет количество и
  выходит без подтверждения: организатор не должен быть узким местом.
- **ordered** — оплачено и отправлено поставщику. Заявки заморожены: изменить
  или снять нельзя, иначе разъедется с реальным заказом.
- **arrived** — привезли, можно забирать (в уведомлении — место выдачи).
- **done** — все забрали. **cancelled** — не собрали или передумали.

Стадии переключает организатор. Цель и дедлайн — ориентир для людей, автоматика
ничего не закрывает: говорить с поставщиком и решать всё равно человеку.

## Экраны

`/poselenie/zakupki` — доска: сбор, затем заказанные и привезённые, завершённые
в конце. На карточке: товар, цена за единицу, полоса «собрано 78 из 100 кг»,
дедлайн, число участников.

`/poselenie/zakupki/{id}` — карточка: прогресс по объёму и деньгам, состав
участников (поместье + количество), форма «участвую». Организатору — кнопки
стадий и отметки оплаты напротив каждого участника.

`/poselenie/zakupki/novaya`, `/{id}/redaktirovat` — формы в стиле раздела
инструментов. `/poselenie/zakupki/moi` — что организую и где участвую.

Доступ — `RequiresHousehold('Закупки')`, как в Книгах, Инструментах, Ярмарке и
Поездках: владелец записи это семья, значит нужно привязанное поместье.

Суммы и состав участников видны всем участникам закупки: для поселения
прозрачность полезнее приватности, а сумма всё равно выводится из количества.
Отметка оплаты видна организатору и самому плательщику.

## Уведомления

На готовой механике `BotNotify` (отправка после ответа, ошибки в лог):

- новая закупка — анонс в группу жителей (`CatalogAnnounce::purchase`);
- организатору лично — новая заявка и выход участника;
- всем участникам лично — «заказано у поставщика» и «привезли, забирайте» с
  местом выдачи.

## Тесты

`PurchaseRepositoryTest` на SQLite: пересчёт собранного объёма и суммы, одна
заявка на семью (повторная правит прежнюю), заморозка заявок после закрытия
сбора, отметка оплаты, переходы статусов, выборки доски и «моих» закупок.

## Границы

Не делаем: прайс-листы из нескольких позиций, приём платежей внутри портала,
автоматическое закрытие по достижении цели, напоминания по дедлайну. Первое —
отдельная задача, остальное противоречит тому, как это работает у людей.

## Развёртывание

Схема — `config/purchases-schema.sql`, накатывается один раз вручную:

```bash
mysql skazkray_residents < config/purchases-schema.sql
```

Раздел появляется в `Sections::LIST` под ключом `zakupki` и по умолчанию
включён; редактор может выключить его на странице «Разделы».
