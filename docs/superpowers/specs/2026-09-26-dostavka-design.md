# Доставка в разделе «Поездки» — дизайн

Дата: 2026-09-26. Раздел жителей (`residents/`). Статус: утверждён, ждёт плана реализации.

## Зачем

Плитка на главной обещает «Поездки — попутчики и доставка», но доставки в приложении нет: есть только брони мест в поездках. Жители постоянно просят соседей, которые едут в город, что-нибудь купить или забрать. Сейчас это идёт в общий чат и теряется.

Ориентир — модуль «Привези» в `C:\Projects\Ride_Share_Bot` (заявка «Привези» / предложение «Привезу»). Берём оттуда идею и одну заявку на одного исполнителя. Сознательно **не** повторяем:
- автоподбор исполнителей;
- подтверждение одной стороной без уведомления другой;
- несколько исполнителей на одну заявку;
- перехват колбэков: кнопки доставки ловятся обработчиками поездок.

## Что получает житель

Два пути:
1. **Просьба к конкретной поездке.** В карточке чужой активной поездки есть кнопка «Попросить привезти». Водитель берёт просьбу или отказывается, как с бронью места.
2. **Заявка на доску «Нужно привезти».** Если подходящей поездки нет. Заявку берёт первый сосед, нажавший «Возьму».

Два типа заявки:
- **«Купить»** — список покупок, где купить, примерная сумма.
- **«Забрать»** — уже оплаченный заказ или посылка, место выдачи, код или номер заказа.

Расчёты идут вне приложения. Приложение фиксирует сумму по чеку, **фото чека** (подтверждение расходов курьера для заказчика) и подтверждение «Получил, рассчитались».

## Данные

Новая таблица `deliveries` (MySQL — миграция `config/deliveries.sql` в конец `config/migrations.txt`; SQLite — та же таблица в `tests/schema.sqlite.sql`):

| Поле | Тип (MySQL) | Смысл |
|---|---|---|
| `id` | INT UNSIGNED AI PK | |
| `requester_id` | INT UNSIGNED NOT NULL, FK families ON DELETE CASCADE | кто просит |
| `carrier_id` | INT UNSIGNED NULL, FK families ON DELETE SET NULL | кто везёт; NULL, пока не взяли |
| `trip_id` | INT UNSIGNED NULL, FK trips ON DELETE SET NULL | поездка, если просьба к водителю |
| `kind` | VARCHAR(8) NOT NULL | `buy` \| `pickup` |
| `what` | TEXT NOT NULL | что купить или забрать, 3–1000 символов |
| `place` | VARCHAR(160) NOT NULL | где: магазин, аптека, пункт выдачи, почта; 2–160 |
| `need_by` | DATE NULL | к какому дню нужно; не в прошлом |
| `budget` | DECIMAL(10,2) NULL | примерная сумма, только `buy`; 0…1 000 000 |
| `pickup_code` | VARCHAR(200) NULL | код или номер заказа, только `pickup` |
| `note` | VARCHAR(500) NULL | комментарий |
| `receipt_sum` | DECIMAL(10,2) NULL | сумма по чеку, вносит исполнитель при «Привёз»; 0…1 000 000 |
| `status` | VARCHAR(16) NOT NULL | см. ниже |
| `created_at` | DATETIME NOT NULL | |
| `accepted_at`, `delivered_at`, `settled_at` | DATETIME NULL | |

Индексы: `(status, need_by)` для доски, `(requester_id)`, `(carrier_id)`, `(trip_id, status)`.

Та же миграция добавляет `INSERT INTO app_sections (section_key, enabled) VALUES ('dostavka', 0)`, чтобы раздел появился выключенным. `Sections::isEnabled` считает неизвестный ключ включённым, поэтому без этой строки раздел включился бы сразу после деплоя.

Места в машине доставка не занимает, `trips.seats_free` не меняется.

**Фото чека** — новой таблицы не нужно: существующая `images` (`ImageRepository::add/listFor`) с `owner_type = 'delivery_receipt'` и `owner_id = deliveries.id`. Только для заявок `buy`, до 3 фото на заявку.

## Жизненный цикл

Статусы:
- `requested` — просьба к поездке, ждёт водителя;
- `open` — на доске;
- `accepted` — взята исполнителем;
- `delivered` — исполнитель привёз;
- `settled` — получено и рассчитались;
- `declined` — водитель отказался;
- `cancelled` — отменена заказчиком.

| Действие | Кто | Из статуса | В статус | Прочее |
|---|---|---|---|---|
| создать к поездке | житель, не водитель; поездка active, дата не в прошлом | — | `requested` | `trip_id` задан |
| создать на доску | житель | — | `open` | анонс в группу |
| «Возьму» | водитель поездки | `requested` | `accepted` | `carrier_id` = водитель |
| «Возьму» | любой, кроме заказчика | `open` | `accepted` | атомарно: `UPDATE … WHERE id=? AND status='open'`; не сработало — «Заявку уже взяли» |
| «Не смогу» | водитель | `requested` | `declined` | |
| «Не смогу» | исполнитель | `accepted` | `open` | `carrier_id`=NULL, `trip_id`=NULL |
| «Отказаться от исполнителя» | заказчик | `accepted` | `open` | `carrier_id`=NULL, `trip_id`=NULL |
| «Выложить на доску» | заказчик | `declined` | `open` | `trip_id`=NULL; анонс в группу |
| «Привёз» | исполнитель | `accepted` | `delivered` | `receipt_sum` и фото чека (оба необязательны, только `buy`) |
| «Добавить фото чека» | исполнитель | `delivered` | `delivered` | только `buy`; если забыл или загрузка не удалась; всего не больше 3 |
| «Получил, рассчитались» | заказчик | `delivered` | `settled` | |
| «Отменить» | заказчик | `requested`, `open`, `accepted` | `cancelled` | |

Отмена или удаление поездки: связанные заявки в `requested` и `accepted` переходят в `open`, `trip_id` и `carrier_id` обнуляются, заказчики получают уведомление. Повторного анонса в группу нет.

Итоговые статусы: `settled`, `cancelled`. Статус `declined` итоговый, пока заказчик не нажмёт «Выложить на доску».

## Экраны и адреса

Раздел живёт внутри «Поездок»: на страницах поездок и доставки вкладки **Поездки | Доставка**. Вкладка «Доставка» и кнопка «Попросить привезти» показываются, только если включён раздел `dostavka`. Плитка на главной не меняется. Доступ — `requireHousehold('dostavka')`. Во всех формах `Csrf::field()`, во всех POST `Csrf::guard()`.

| Адрес | Что |
|---|---|
| `GET /poselenie/dostavka` | доска «Нужно привезти»: `open`, `need_by` ≥ сегодня или пусто, ближайшие по сроку сверху, фильтр по типу; кнопки «+ Попросить привезти», «Мои доставки» |
| `GET /poselenie/dostavka/novaya` | форма; `?poezdka=ID` — просьба к поездке, сверху карточка «Просьба к поездке А → Б, дата, водитель» |
| `POST /poselenie/dostavka/novaya` | создать |
| `GET /poselenie/dostavka/moi` | «Мои доставки»: «Я прошу», «Я везу», «Просьбы к моим поездкам» |
| `GET /poselenie/dostavka/{id}` | карточка; регистрируется последней среди GET, как у поездок |
| `POST /poselenie/dostavka/{id}/vzyat` | «Возьму» |
| `POST /poselenie/dostavka/{id}/ne-smogu` | «Не смогу» |
| `POST /poselenie/dostavka/{id}/snyat-ispolnitelya` | «Отказаться от исполнителя» |
| `POST /poselenie/dostavka/{id}/privez` | «Привёз», поля `receipt_sum` и `photos[]` (multipart) |
| `POST /poselenie/dostavka/{id}/chek` | «Добавить фото чека», поле `photos[]` |
| `POST /poselenie/dostavka/{id}/rasschitalis` | «Получил, рассчитались» |
| `POST /poselenie/dostavka/{id}/na-dosku` | «Выложить на доску» |
| `POST /poselenie/dostavka/{id}/otmenit` | «Отменить» |

Форма:
- «Тип»: Купить / Забрать;
- «Что купить» / «Что забрать» — подпись по типу;
- «Где»;
- «К какому дню (необязательно)»;
- «Примерная сумма, ₽» — только «Купить»;
- «Код или номер заказа» — только «Забрать», с пометкой «увидит только тот, кто возьмёт заявку»;
- «Комментарий (необязательно)»;
- кнопка «Попросить привезти».

Поля по типу скрываются скриптом. Без скрипта видны все, сервер игнорирует поле не своего типа.

Карточка показывает только действия, которые `DeliveryPolicy` разрешает этому человеку в этом статусе. Код получения виден заказчику и текущему исполнителю, если он назначен.

Фото чека:
- форма «Привёз» у заявки «Купить»: поле «Сумма по чеку, ₽» и кнопка «Приложить фото чека» (до 3, превью перед отправкой, как в форме закупки);
- в карточке блок «Чек»: сумма и миниатюры с увеличением по нажатию (как галерея закупки); виден **только заказчику и исполнителю**;
- у исполнителя в статусе `delivered` кнопка «Добавить фото чека», пока фото меньше 3.

Загрузка — так же, как у закупок и инструментов: `TelegramMedia::upload` (путь `tg:<file_id>`), при недоступности Telegram — `Upload::saveImage` в `uploads_dir`. Ошибки загрузки (размер, формат, мегапиксели) — flash из `Upload`; статус «Привёз» при этом всё равно ставится, фото можно добавить потом.

Приватность — осознанный компромисс, выбранный владельцем: как и остальные фото приложения, чек попадает в Telegram-канал медиа и открывается по прямой ссылке (`/tg-media/<id>.jpg` или `/poselenie/uploads/<имя>`) без проверки прав. Интерфейс показывает чек только сторонам заявки; ссылка на чек не попадает в уведомления и анонсы.

Правки поездок:
- `trip/show.php` — кнопка «Попросить привезти» для не-водителя при активной будущей поездке;
- `trip/mine.php` — блок «Просьбы привезти» с «Возьму» / «Не смогу»;
- `trip/board.php` — вкладки;
- `TripController::cancelTrip` и `delete` — отвязка заявок и уведомления.

## Уведомления

Письмо через `Mailer::later` и сообщение бота через `BotNotify::personal` уходят последними, после `Flash::set` и `header('Location')`, как в `TripBookingController`.

| Событие | Кому | Бот |
|---|---|---|
| просьба к поездке | водителю | «📦 Просьба привезти» · тип · что · где · к какому дню · заказчик · «Взять или отказаться: » → `/dostavka/moi` |
| «Возьму» | заказчику | «✅ Заявку взяли» · исполнитель (`family_contact`) |
| водитель «Не смогу» | заказчику | «🚫 Водитель не сможет привезти» · «Можно выложить заявку на общую доску: » → карточка |
| исполнитель «Не смогу» | заказчику | «↩️ Исполнитель не сможет — заявка снова на доске» |
| «Отказаться от исполнителя» | бывшему исполнителю | «↩️ Заказчик снял вас с заявки» |
| «Привёз» | заказчику | «📦 Привезли» · «Сумма по чеку: N ₽» (если указана) · «Фото чека — в карточке заявки» (если приложено) · «Отметьте получение: » → карточка |
| «Получил, рассчитались» | исполнителю | «🤝 Получение и расчёт подтверждены» |
| «Отменить» | водителю или исполнителю, если был | «🚫 Заявка отменена» |
| отмена или удаление поездки | заказчикам | «Поездка отменена — ваша заявка теперь на общей доске» |

Анонс в группу (`CatalogAnnounce::delivery`): при создании заявки на доску и при «Выложить на доску». Текст: «📦 Нужно привезти», строка «Купить · <где> · к <дата>», ссылка на карточку. Поле `what` в анонс **не попадает**: там может быть личное (лекарства), детали видны только в приложении.

Код получения (`pickup_code`) не попадает ни в одно уведомление, письмо или анонс.

## «Мои дела»

В `MyTasks` два новых вида:
- `delivery_request` — водителю: заявка `requested` к его активной поездке, дата которой не в прошлом → `/dostavka/moi`;
- `delivery_confirm` — заказчику: заявка `delivered` → карточка.

Оба учитывают включённость раздела `dostavka`.

## Модули

| Модуль | Ответственность |
|---|---|
| `Repository/DeliveryRepository` | SQL: create, findDetailed (с именами и контактами сторон, поездкой), listBoard, listByRequester, listByCarrier, listForTripDriver, take (атомарный), setStatus с датами, release (на доску), releaseTripRequests(tripId) |
| `Service/DeliveryPolicy` | чистая логика без БД: `actions(delivery, userId, tripDriverId)` → список допустимых действий; единый источник правил и для контроллера, и для шаблона |
| `Service/DeliveryNotify` | тексты и отправка; `*Text()` отдельно от отправки для тестов |
| `CatalogAnnounce::delivery` | анонс в группу |
| `Controller/DeliveryController` | HTTP: `RequiresHousehold`, CSRF, валидация, проверка через `DeliveryPolicy`, flash, редиректы, уведомления; загрузка фото чека (`handleReceiptUploads`, как `handleUploads` у закупок, с лимитом 3) |
| `templates/delivery/{board,form,show,mine}.php` | экраны |
| `Sections::LIST['dostavka'] = 'Доставка'` | переключатель |

Чужое действие — 403 «Доступ запрещён.». Действие не из текущего статуса — flash «Заявка уже обработана.» и возврат на карточку.
